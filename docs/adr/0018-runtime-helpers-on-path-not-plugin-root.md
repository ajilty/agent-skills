# Runtime helpers resolve via plugin `bin/` on PATH, not `${CLAUDE_PLUGIN_ROOT}`

The router and the Planner persona invoke the runtime helpers by bare name
(`ledger.sh reground`, `adr.sh reindex`, `adr.sh add`, `worktree.sh create`). Field
failure on Claude Code: a run reported `adr.sh` "doesn't exist" and hand-rolled an ADR,
because the documented command resolved nowhere. The script does exist (it ships in the
plugin runtime); the bug is that the bare invocation is unresolvable as written.

What testing established (Claude Code 2.1.196, marketplace install):

- The helpers live at `<plugin>/skills/orchestrate/runtime/`. That dir is not on PATH;
  `command -v ledger.sh` / `adr.sh` fails from any cwd, in the router **and** in spawned
  personas.
- `${CLAUDE_PLUGIN_ROOT}` (the plugin-dev convention for intra-plugin paths) is **unset**
  in skill Bash and in subagent Bash. It is injected only into hook commands, MCP args,
  and slash-command bash, none of which orchestrate uses to call these helpers. So
  `bash ${CLAUDE_PLUGIN_ROOT}/.../adr.sh` typed by the router/persona expands to
  `bash /.../adr.sh` and fails. The variable is supplied by the *launcher* (hook runner,
  MCP spawner, command executor); orchestrate's launcher is the LLM reading skill prose
  and spawning personas, which is outside that variable's reach.
- Claude Code adds `<plugin>/bin` to PATH unconditionally, for the main agent **and** for
  spawned subagents (both observed). The plugin shipped no `bin/`, so the mechanism was
  unused.
- A `bin/` shim that self-locates the real helper
  (`exec "$(dirname "$0")/../skills/orchestrate/runtime/<n>"`) makes bare `adr.sh` resolve
  and run from an arbitrary cwd (verified end-to-end). The helper's own `docs/adr`-relative
  behaviour is unaffected because the locating `cd` runs in a subshell, so the exec'd
  helper keeps the caller's cwd.
- Hooks already resolve correctly (`build.sh` bakes `${CLAUDE_PLUGIN_ROOT}/.../hooks` into
  `hooks.json`, expanded by the hook runner). Only the LLM-facing call sites were broken.

**Decision.** Expose the runtime helpers (`ledger.sh`, `adr.sh`, `worktree.sh`) on PATH so
the documented bare invocation is true in every execution context, using each harness's
native PATH lever rather than `${CLAUDE_PLUGIN_ROOT}` (unreachable from skill prose and
spawned personas):

| Harness | Lever |
|---|---|
| Claude Code | Commit `<plugin>/bin/{ledger,adr,worktree}.sh` self-locating shims; Claude Code's automatic `<plugin>/bin` PATH entry covers the router and every persona. |
| Codex | `dispatch-persona.sh` prepends the runtime dir to PATH before `codex exec` (personas run with cwd = lane subtree). |
| opencode | The plugin (`orchestrate.ts`) prepends the runtime dir to `process.env.PATH` at load. |

The helpers stay single-source under `skills/orchestrate/runtime/`; `bin/` holds only
shims. SKILL prose stays bare-name (now correct everywhere); the stray `runtime/adr.sh`,
`runtime/worktree.sh`, and `runtime/ledger.sh` references in SKILL.md are normalized to
bare, since `runtime/X` was also broken from the repo cwd.

## Considered options
- **`${CLAUDE_PLUGIN_ROOT}/...` absolute paths in prose** (the documented convention) —
  rejected: the variable is unset in skill/persona Bash, the exact contexts orchestrate
  calls from; it expands to empty and the call fails. It works only where a launcher
  injects it (hooks/MCP/commands).
- **Symlinks in `bin/` instead of shims** — workable (no helper resolves siblings via
  `$0`; `ledger.sh`'s `bash "$0"` self-reexec survives a symlink), but a shim is explicit,
  self-documents, and survives a future sibling-via-`$0` dependency. Chose shims; the cost
  is three tiny files.
- **A SessionStart hook exporting the path** — rejected: each Bash tool call is a fresh
  shell; hook-exported env does not persist into later tool calls.
- **Bake an absolute path into SKILL.md at build time** — rejected: the skill is committed
  and machine-independent; an absolute path is not portable across clones, users, or
  harnesses.

## Consequences
- Fixes the reported field failure on Claude Code with no prose rewrite beyond
  normalization. Router and personas both resolve `ledger.sh`/`adr.sh`/`worktree.sh` by
  bare name. Covered by `tests/test_runtime_resolution.sh`.
- Deviates from the plugin-dev `${CLAUDE_PLUGIN_ROOT}` guidance for these call sites, with
  the evidence above; the `plugin-validator` agent may flag it. Hooks remain
  `${CLAUDE_PLUGIN_ROOT}`-based (correct). The shim comments and this ADR carry the
  rationale.
- `bin/` is hand-authored static (like `plugin.json`), not generated by `build.sh`, so the
  committed-equals-fresh-build drift guard is unaffected.
- **Codex router PATH is a known follow-up.** `dispatch-persona.sh` puts the runtime dir on
  PATH for the personas *it* launches, but the Codex main agent (router) inherits the PATH
  of wherever `codex` was started. Putting the runtime dir on the router's PATH needs a
  check of Codex `shell_environment_policy` semantics (set vs. prepend) and is deferred
  rather than shipped unverified. The opencode `process.env.PATH` prepend likewise assumes
  env propagates to the bash tool in that OpenCode version; flagged in-comment.
- Delivery requires a version bump + marketplace re-pull: a marketplace install runs no
  build and is keyed on version, so the committed `bin/` reaches users only under a new
  plugin version.

## Status

active (implemented; Claude Code + Codex-persona + opencode paths shipped, Codex-router PATH deferred)
